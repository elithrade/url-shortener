- [x] Sweep cost measured (throwaway experiments in collision-lab: `dotnet run -c Release -- sweep` and `-- stores`, Release build, 8 logical processors, median of 3 runs). **Current store (`Dictionary` + one lock):** the sweep scales linearly, about 8 to 11 ms per million entries to scan and 46 to 54 ms per million when everything expires (1M: 11 / 17 / 46 ms for none / 10% / all expired; 5M all expired: 269 ms), and a concurrent `GetAsync` waits for the *whole* sweep (worst latency equals the sweep time, 41 ms at 1M all expired, against about 0.05 ms idle) because the sweep holds the lock throughout. **`ConcurrentDictionary` twin** (experiment-only, same interfaces): the reader is never blocked (worst 0.01 to 0.25 ms), but the sweep is 3 to 7 times slower (1M: 56 ms scan-only, 152 ms all expired), memory is about 10% higher (218 MB against 199 MB), and 8 reader threads reach 484 million reads/s against 15 million for the lock (the lock version gets *slower* as threads are added: 73, 51, 25, 15 million at 1, 2, 4, 8 threads). That throughput gap is synthetic: a real request costs microseconds, so the lock is held about 0.02% of the time at 4,000 requests per second. Source reading (`ConcurrentDictionary.cs`): reads take no lock, writers take one stripe of a lock array (default `Environment.ProcessorCount` locks), `TryRemove` locks per entry, and `Count`, `ToArray`, `Keys`, `Values` and `Clear` take all locks. **`ToArray()` memory:** `Where().ToArray()` allocates 16 bytes per *expired* entry (a key/value reference pair; the strings and entries are not copied): 15.3 MB at 1M all expired and 76.3 MB at 5M, about 8% of the store's roughly 200 bytes per entry, so the store runs out of memory long before the temporary array does. The first sweep in a process allocated up to 2.5x that (a one-time LINQ warm-up, observed and not explained), and there were no gen2 GCs. **Alternatives, measured on a replica `Dictionary`:** removing in place while enumerating allocates 0 bytes, is about 2x faster (25 against 49 ms at 1M all expired; 165 against 275 ms at 5M) and did not throw on .NET 10, while a `Take(10,000)` batch cap that rescans from the start is much *slower* (91 ms at 1M and 1.35 s at 5M all expired; 1.5 s against 76 ms at 5M with 10% expired), because every batch walks the dictionary again. **Decision:** keep `Dictionary` + lock with the brute-force O(n) sweep, with no cap and no `PriorityQueue`: it is the simple, correct choice at this scale, the in-memory store is a stand-in for a database store (which will need its own sweep, since Postgres has no native TTL), and the limits above are recorded for reference

- [x] Redis lab (hands-on in `redis-cli` in a `redis:7` container; no code in this repo yet). Decision (revised the same day): the first plan was Redis as the store, with SQL added later for users. The lab showed Redis is priced in RAM (about 150 GB per billion keys) and, with AOF `everysec`, can lose about a second of acknowledged writes, so the decision is **Postgres as the source of truth (milestone 5) and Redis as a read-through cache in front of it (Line 2, item B)**. The lab findings below still apply to that cache. (Polyglot persistence was the other side of this: a second system to run and back up, and no transaction across two stores.) **Verified by running it:** `SET k v NX EX 30` is an atomic insert-if-absent with an expiry (`OK` the first time, `(nil)` on a collision, and a failed `NX` leaves the old value and its TTL alone), which is exactly `TryAddAsync`. `TTL` returns -1 for "exists, no expiry" and -2 for "no such key", and an expired key reads as missing. A plain `SET` on an existing key discards its TTL, so the store should only ever write with `NX`. `EX 0` and `PX -5` are errors (`invalid expire time`), so a past `ExpiresAt` can't be written. Redis removed 1,000 expired keys nobody read, within 3 s. **From the docs, not tested separately:** expiry is passive (checked on access) plus active (periodic sampling of keys with a TTL), so a read never returns an expired key and `RedisUrlStore.GetAsync` needs no read-time expiry check. **Persistence:** with the defaults (`save 3600 1 300 100 60 10000`, `appendonly no`) a SIGKILL loses everything since the last snapshot (a killed container lost its key), while a SIGTERM (`docker stop`) writes a final `dump.rdb` and loses nothing. With `--appendonly yes` a write survived `docker kill`, and `appendfsync` defaults to `everysec` (a crash can lose about a second of writes; the docs may say up to 2, check). Starting with AOF on a volume that only has `dump.rdb` silently ignored the snapshot (`GET old` returned nil, the file was still there), so choose the persistence mode before real data exists. A container needs a volume on `/data`, and `--rm` plus no volume made my first restart test meaningless. **Memory (100,000 keys, 7-char key, 40-char value, 30-day TTL):** 149.7 bytes per key (987,000 to 15,958,344 bytes), `MEMORY USAGE` for one key says 104, and the TTL adds about 24 bytes per key (my guess: the separate expiry table, not verified). At 1 billion keys that is about 150 GB before replicas, longer URLs or fork headroom, so Redis as the only store at that scale is expensive (10M links is about 1.5 GB). **Eviction:** with `maxmemory 3mb` and the default `noeviction`, 13,584 of 100,000 `SET`s succeeded and 86,416 failed with `OOM command not allowed`. With `allkeys-lru` all 100,000 returned `OK`, `DBSIZE` ended at 13,464, and the first key was gone, so live links were deleted silently. Decision when Redis was going to be the store: `maxmemory-policy noeviction`, `maxmemory` below the machine's RAM, an alert on `used_memory`, and the OOM error mapped to 503. Redis does not spill to disk, and a managed Redis may default to eviction, so check before using one as a store. As a cache (the revised plan) the choice flips: eviction is the point, so item B decides between an LRU-style policy and others, and a lost cache entry only costs a re-read from Postgres
- [x] Postgres lab (hands-on in a `postgres:17` container with a named volume, table `links (code text PRIMARY KEY, url text NOT NULL, expires_at timestamptz)`; no code in this repo yet). **Atomic insert:** `INSERT ... ON CONFLICT DO NOTHING` reports rows affected (`INSERT 0 1` for a new code, `INSERT 0 0` for a collision), which maps straight to `TryAddAsync` returning `true` or `false` with no exception. A plain `INSERT` of an existing key throws a unique violation (SQLSTATE `23505`, constraint `links_pkey`, and the message contains the key, so it must never reach an API response). `DO NOTHING` also returns 0 for an expired row that hasn't been swept, so an expired code stays unusable until the sweeper deletes it (the same rule as the in-memory store; kept as a decision). **Race:** 50 parallel inserts of one code (50 `docker exec` processes, not simultaneous, so evidence rather than proof) gave exactly 1 `INSERT 0 1` and 49 `INSERT 0 0`, and one row, with no lock in our code; the plain form gave 1 success and 49 errors. **Why uniqueness needs no app lock:** a second session inserting a key that an open transaction has inserted waits (`pg_stat_activity`: `Lock` / `transactionid`, while the first shows `idle in transaction`), then returns `INSERT 0 0` after the first commits and `INSERT 0 1` after it rolls back. **Delete and dead tuples (1M rows, half expired):** `DELETE` of 500,000 rows took 199 ms on an idle server (the in-memory sweep is roughly 8x faster, by the earlier measurements), but the table stayed 73 MB (110 MB with indexes), `n_dead_tup` was 500,000 and `count(*)` 500,000, because a delete only ends a row version and the space is freed by vacuum. Autovacuum had already cleaned it by the time I ran `VACUUM` (`n_dead_tup` 0, 4 ms). A plain vacuum makes the space reusable inside the file and does not shrink it: inserting 500,000 new rows left the table at 73 MB (the indexes grew, 110 to 125 MB total), and `VACUUM FULL` rewrote the table in about 1.6 s to 73 MB table and 110 MB total. **Lock queue:** with one session holding an open read transaction, `VACUUM FULL` had to wait for it, and an ordinary read that started after `VACUUM FULL` queued behind it for about 4.8 s (`blocked_by` showed the read blocked by `VACUUM FULL`, itself blocked by the open transaction), while a read that started before returned in about 190 ms. An idle-in-transaction session plus a command that needs an exclusive table lock can stall every read; I expect schema-changing migrations to behave the same way (inferred, to verify before the first deploy). **Sweep against readers:** 4 clients doing primary-key lookups for 12 s: baseline 374,078 reads, average 0.128 ms, worst 4.9 ms; during one `DELETE` of 500,000 rows (380 ms with readers running) 366,782 reads, average 0.131 ms, worst 6.1 ms, 3 reads over 5 ms; during the same delete in 50 batches of 10,000, 381,221 reads, worst 3.9 ms, but the whole delete took 4,255 ms (about 11x longer). Readers are not blocked (unlike the in-memory lock), and batching only costs time at this size, so **decision: one `DELETE` per sweep, no batch cap**. Not covered: scans by `expires_at`, concurrent inserts, replication and WAL volume, tables 100x larger, and one run per scenario. **Durability:** defaults read from the server are `fsync`, `synchronous_commit`, `full_page_writes` and `autovacuum` all `on`. After `docker kill`, a committed row survived and a row inside an open `BEGIN` did not (the log said `database system was not properly shut down; automatic recovery in progress`, then `redo starts` and `redo done`). The `invalid record length ... got 0` line is, I believe, the normal end of the log, not an error (not verified). A commit waits for the write-ahead log to reach disk, unlike Redis `everysec`
- [x] Contract rule for a past expiry, and the start of the contract tests: `IUrlStore.TryAddAsync` rejects an `ExpiresAt` that is not in the future with `ArgumentOutOfRangeException(nameof(linkEntry), "ExpiresAt must be in the future")`, before the lock and before the insert. `ExpiresAt == now` counts as past, matching the read rule `now >= ExpiresAt`, and a null `ExpiresAt` (never expires) is accepted because comparisons on a nullable are false for null (commented in the code, and `Sweep` relies on the same rule). Why it is a store rule: Redis rejects `EX 0` and negative values, and nothing else would stop a store storing a pre-expired entry. Open design note for persistence (milestone 5): reads never delete, so the sweep is the only thing that frees a code for reuse, and a swept code can be issued again. That is accepted for the in-memory store. At large scale the expected number of reissued old codes is about `old x new / 3.5 trillion` (28 at 10M and 10M, about 285,000 at 1B and 1B), so the persistent store needs a never-reissue policy. Postgres has no native TTL, so the sweeper's `DELETE` is what frees a code, and the options are: keep expired rows and only hide them (the table grows, but a code is never reused, and reads already filter on `expires_at`), delete the row but record the code in a small tombstone table, or use counter-based codes (a Bloom filter of issued codes is the in-memory alternative). This is also the milestone 8 ID-allocation topic.
